# Довідник CLI digna 2026.06
**2026-09-05**

На цій сторінці описано повний набір команд, доступних у випуску **2026.06** CLI ***digna***, разом із прикладами використання та параметрами.

Виконуваний файл має назву `digna`.

---

## Основи CLI

---

### Огляд і синтаксис

CLI випуску **2026.06** використовує структуровану ієрархію команд, побудовану за категоріями:

```bash
digna [GLOBAL_OPTIONS] <COMMAND_CATEGORY> <SUBCOMMAND> [OPTIONS] [ARGUMENTS]
```

`version` і `serve` — це окремі команди без підкоманди:

```bash
digna [GLOBAL_OPTIONS] <COMMAND> [OPTIONS] [ARGUMENTS]
```

### Глобальні параметри

Наведені нижче глобальні параметри діють для всіх команд:

- `--help`, `-h`: Показує довідкову інформацію про CLI або про конкретну категорію команд чи підкоманду.
- `--stacktrace`: У разі помилки показує весь ланцюжок помилок замість самого лише повідомлення верхнього рівня.

`--stacktrace` є глобальним параметром у строгому сенсі: його потрібно вказувати **перед** категорією команд, а не після неї.

```bash
digna --stacktrace repo check     # correct
digna repo check --stacktrace     # rejected: unknown argument
```

Прапорця `--version` не існує. Натомість скористайтеся командою [`version`](#version).

### Передумови

Більшість команд потребують придатного до читання й коректного файлу `config.toml`; деякі додатково вимагають чинної ліцензії.
У наведеній нижче таблиці зафіксовано, що завантажує кожна категорія команд, перш ніж що-небудь зробити:

| Категорія команд | Потрібен `config.toml` | Потрібна чинна ліцензія |
|---|---|---|
| `version` | ні | ні |
| `config check` | ні (саме про нього команда й звітує) | ні |
| `license check` | ні | вона *і є* цією перевіркою |
| `crypt` | так | ні |
| `serve` | так | ні |
| `project` | так | ні |
| `user` | так | так |
| `inspection` | так | так |
| `repo` | так | так |

Там, де потрібна ліцензія, перевіряються і її підпис, і термін дії, і команда завершується, не торкаючись репозиторію, якщо бодай одна з цих перевірок не пройдена.

### Коди завершення

- `0`: команда виконана успішно.
- `1`: команда завершилася помилкою. Повідомлення про помилку записується до stderr із префіксом `Error: `.

### help

Параметр `--help` надає відомості про доступні категорії команд, підкоманди та параметри:

1. **Показ загальної довідки:**
   ```bash
   digna --help
   ```

2. **Отримання довідки для конкретних категорій і команд:**
   ```bash
   digna user --help
   digna user add --help
   ```

   **Вивід містить:**
   - **Опис команди:** Стислий виклад призначення команди.
   - **Синтаксис:** Обов'язкові та необов'язкові аргументи.
   - **Параметри:** Прапорці та параметри, властиві саме цій команді.

### version

Команда `version` виводить встановлений випуск ***digna***. Вона не читає конфігурації й не перевіряє ліцензії, тому працює й у встановленні, де файл `config.toml` чи ліцензія відсутні або некоректні.

Версія випуску не пов'язана з версією схеми репозиторію, про яку звітує [`repo check`](#repo-check).

#### Використання команди
```bash
digna version
```

#### Приклад виводу
```text
2026.06
```

## Керування конфігурацією

---

### config check

Команда `config check` перевіряє файл конфігурації (`config.toml`), встановлюючи, чи всі обов'язкові розділи та налаштування наявні й правильно оформлені. Кожен розділ перевіряється окремо, тож пошкоджений розділ `[app]` не приховує стану розділу `[repo]`.

Звіт охоплює такі розділи:

- `App config` (`[app]`)
- `Repository config` (`[repo]`)
- `Base config` (`[base]`)
- `Logging config` (`[logging]`)
- `Encryption config` (`[encryption]`)
- `OIDC config(s)` (`oidc_clients`) — необов'язковий; відсутній ключ перевірку проходить, а наявний, але хибно оформлений список — ні

Команда навмисно не завантажує конфігурацію застосунку так, як це роблять інші команди, щоб мати змогу діагностувати файл `config.toml`, який узагалі не дав би ***digna*** запуститися.

#### Використання команди
```bash
digna config check [OPTIONS]
```

#### Параметри
- `--configpath`, `-c`: Шлях до файлу конфігурації або до каталогу, що містить `config.toml` (типово `./config.toml`).
- `--json`: Виводить звіт перевірки у форматі JSON. Має пріоритет над `--quiet`.
- `--quiet`, `-q`: Приховує звіт і покладається виключно на код завершення.

#### Приклад
```bash
digna config check
```

Перевірити конкретний файл конфігурації та вивести результат у форматі JSON:
```bash
digna config check --configpath /etc/digna/config.toml --json
```

#### Приклад виводу
```text
Configuration validation report (source: config.toml):
 - App config: OK
 - Repository config: OK
 - Base config: OK
 - Logging config: OK
 - Encryption config: FAILED
    missing field `aes_gcm_key`
 - OIDC config(s): OK

Overall: FAILED
```

Відсутній файл або синтаксична помилка TOML не лишають нічого, що можна було б перевіряти розділ за розділом, і повідомляються як одна помилка замість звіту — незалежно від `--quiet` чи `--json`.

## Керування репозиторієм

---

### repo check

Команда `repo check` перевіряє з'єднання з базою даних, а також встановлення та версію репозиторію. Вона завершується помилкою, якщо налаштованої схеми не існує або якщо схема існує, але не містить репозиторію ***digna***.

Версія, про яку звітує команда, — це версія схеми репозиторію, що версіонується окремо від випуску ***digna***, який виводить [`version`](#version).

#### Використання команди
```bash
digna repo check
```

#### Приклад виводу
```text
Repo version 3.0.0 installed
```

### repo install

Команда `repo install` встановлює новий репозиторій ***digna*** у схему, налаштовану в `config.toml`, створюючи всі потрібні послідовності, таблиці, індекси, обмеження та початкові записи.

Саму схему ця команда **не** створює — вона має існувати заздалегідь. Команда також відмовляється виконуватися, якщо репозиторій у цій схемі вже встановлено, і вказує на [`repo upgrade`](#repo-upgrade), якщо встановлено старішу версію.

#### Використання команди
```bash
digna repo install
```

#### Приклад виводу
```text
Installing repo version 3.0.0
✅ Sequences created.
✅ Tables and Indices created.
✅ Constraints created.
✅ Records inserted.
✅ Repo version 3.0.0 successfully installed.
```

### repo upgrade

Команда `repo upgrade` застосовує міграції схеми бази даних, щоб привести наявний репозиторій до версії, якої очікує встановлений випуск. Оновлення застосовуються по одному переходу між версіями за раз уздовж фіксованого шляху оновлення, і кожен завершений перехід записується в репозиторії.

Якщо репозиторій уже має очікувану версію, команда повідомляє, що оновлення не потрібне, і нічого не змінює.

#### Використання команди
```bash
digna repo upgrade
```

#### Приклад виводу
```text
Upgrading from 2.3.1 to 2.3.2...
Upgrading from 2.3.2 to 3.0.0...
✅ Repo successfully upgraded to version 3.0.0.
```

## Керування шифруванням

---

### crypt gen-key

Команда `crypt gen-key` генерує новий ключ шифрування AES-GCM для використання як ключа шифрування у `config.toml`. Придатний до завантаження файл `config.toml` уже має бути наявним, хоча згенерований ключ від нього й не залежить.

#### Використання команди
```bash
digna crypt gen-key
```

#### Приклад виводу
```text
Encryption key: <base64-encoded key>
```

### crypt encrypt

Команда `crypt encrypt` шифрує рядок (наприклад, пароль до бази даних) за допомогою ключа AES-GCM, налаштованого у `config.toml`, і виводить шифротекст.

#### Використання команди
```bash
digna crypt encrypt <VALUE>
```

#### Аргументи
- **VALUE**: Відкритий рядок, який потрібно зашифрувати (обов'язковий).

#### Приклад
```bash
digna crypt encrypt mysecretpassword
```

### crypt decrypt

Команда `crypt decrypt` розшифровує рядок, зашифрований алгоритмом AES-GCM, за допомогою ключа, налаштованого у `config.toml`, і виводить відкритий текст.

#### Використання команди
```bash
digna crypt decrypt <VALUE>
```

#### Аргументи
- **VALUE**: Зашифрований рядок, який потрібно розшифрувати (обов'язковий).

#### Приклад
```bash
digna crypt decrypt "encrypted_string_here"
```

## Керування користувачами

---

### user add

Команда `user add` створює новий обліковий запис користувача в репозиторії ***digna***. Команда завершується помилкою, якщо користувач із вказаною адресою електронної пошти вже існує.

#### Використання команди
```bash
digna user add <EMAIL> <PASSWORD> <DISPLAY_NAME> [OPTIONS]
```

#### Аргументи
- **EMAIL**: Адреса електронної пошти користувача (обов'язковий).
- **PASSWORD**: Початковий пароль користувача (обов'язковий).
- **DISPLAY_NAME**: Повне відображуване ім'я користувача (обов'язковий).

#### Параметри
- `--admin`, `-a`: Створює користувача з правами адміністратора (суперкористувача).

#### Приклад
```bash
digna user add jdoe@example.com "SecurePass123!" "John Doe"
```

Створення облікового запису адміністратора:
```bash
digna user add admin@example.com "AdminPass123!" "Admin User" --admin
```

#### Приклад виводу
```text
User created with ID: 42
```

### user list

Команда `user list` виводить усіх зареєстрованих користувачів у вигляді таблиці з ідентифікатором, адресою електронної пошти, відображуваним іменем і ознакою адміністратора.

#### Використання команди
```bash
digna user list
```

#### Приклад виводу
```text
ID                   EMAIL                          DISPLAY NAME                   ADMIN
-----------------------------------------------------------------------------------------------
42                   jdoe@example.com               John Doe                       false
43                   admin@example.com              Admin User                     true
```

### user modify

Команда `user modify` оновлює відображуване ім'я та права адміністратора наявного облікового запису користувача, визначеного за адресою електронної пошти.

І відображуване ім'я, і ознака адміністратора записуються завжди. `--admin` — це перемикач, а не значення: **якщо його не вказати, права адміністратора буде відкликано**, тож вказуйте його щоразу, коли користувач має зберегти або отримати ці права.

#### Використання команди
```bash
digna user modify <EMAIL> <DISPLAY_NAME> [OPTIONS]
```

#### Аргументи
- **EMAIL**: Адреса електронної пошти користувача, якого потрібно змінити (обов'язковий).
- **DISPLAY_NAME**: Оновлене відображуване ім'я (обов'язковий).

#### Параметри
- `--admin`, `-a`: Надає права адміністратора. Не вказуйте, щоб відкликати їх.
- `--valid-until`, `-v`: Приймається задля сумісності, але **наразі не застосовується**. Його передавання виводить попередження й нічого не змінює.

#### Приклад
```bash
digna user modify jdoe@example.com "Johnathan Doe" --admin
```

#### Приклад виводу
```text
User jdoe@example.com modified successfully
```

### user modify-pwd

Команда `user modify-pwd` оновлює пароль наявного облікового запису користувача.

#### Використання команди
```bash
digna user modify-pwd <EMAIL> <PASSWORD>
```

#### Аргументи
- **EMAIL**: Адреса електронної пошти користувача, чий пароль потрібно оновити (обов'язковий).
- **PASSWORD**: Новий пароль (обов'язковий).

#### Приклад
```bash
digna user modify-pwd jdoe@example.com "NewSecurePass456!"
```

### user delete

Команда `user delete` вилучає обліковий запис користувача із системи.

#### Використання команди
```bash
digna user delete <EMAIL>
```

#### Аргументи
- **EMAIL**: Адреса електронної пошти користувача, якого потрібно видалити (обов'язковий).

#### Приклад
```bash
digna user delete jdoe@example.com
```

## Керування проєктами та джерелами даних

---

### project list

Команда `project list` виводить усі доступні в репозиторії проєкти з їхнім ідентифікатором, назвою та описом.

#### Використання команди
```bash
digna project list
```

#### Приклад виводу
```text
ID                   NAME                           DESCRIPTION
------------------------------------------------------------------------------------------------------
7                    ProjectA                       Sales data quality
8                    ProjectB                       Finance data quality
```

### project list-ds

Команда `project list-ds` виводить усі джерела даних, пов'язані з певним проєктом, показуючи їхній ідентифікатор, назву, вид, схему та назву таблиці.

#### Використання команди
```bash
digna project list-ds <PROJECT_NAME>
```

#### Аргументи
- **PROJECT_NAME**: Назва проєкту, джерела даних якого потрібно вивести (обов'язковий). Назва має збігатися точно.

#### Приклад
```bash
digna project list-ds ProjectA
```

#### Приклад виводу
```text
ID                   NAME                           KIND            SCHEMA               TABLE
-------------------------------------------------------------------------------------------------------------
101                  orders                         Table           sales                orders
102                  customers                      Table           sales                customers
```

### project export-ds

Команда `project export-ds` експортує джерела даних проєкту до документа JSON.

Якщо не вказано ні `--table-name`, ні `--table-id`, експортуються всі джерела даних проєкту.

#### Використання команди
```bash
digna project export-ds <PROJECT_NAME> [OPTIONS]
```

#### Аргументи
- **PROJECT_NAME**: Назва проєкту, з якого експортуються джерела даних (обов'язковий).

#### Параметри
- `--table-name`, `-n`: Назви джерел даних для експорту. Кілька назв можна вказати через пробіл.
- `--table-id`, `-i`: Ідентифікатори джерел даних для експорту. Кілька ідентифікаторів можна вказати через пробіл.
- `--exportfile`, `-f`: Шлях, за яким зберігаються експортовані джерела даних (типово: `data_sources_export.json`).

#### Приклад
Щоб експортувати всі джерела даних із `ProjectA`:
```bash
digna project export-ds ProjectA --exportfile my_export.json
```

Щоб експортувати окремі таблиці:
```bash
digna project export-ds ProjectA --table-name users orders -f users_orders_export.json
```

#### Приклад виводу
```text
Successfully exported 2 data source(s) to users_orders_export.json
```

### project import-ds

Команда `project import-ds` імпортує джерела даних із файлу експорту до цільового проєкту й повідомляє щодо кожного об'єкта, що було створено, оновлено чи пропущено.

#### Використання команди
```bash
digna project import-ds <PROJECT_NAME> <EXPORT_FILE> [OPTIONS]
```

#### Аргументи
- **PROJECT_NAME**: Назва цільового проєкту, до якого виконується імпорт (обов'язковий).
- **EXPORT_FILE**: Шлях до файлу експорту у форматі JSON (обов'язковий).

#### Параметри
- `--output-file`, `-o`: Файл, до якого записується звіт про імпорт. Без нього звіт виводиться до stdout.
- `--output-format`, `-f`: Формат звіту про імпорт — `table`, `json` або `csv` (типово: `table`).

#### Приклад
```bash
digna project import-ds ProjectB my_export.json
```

Щоб отримати звіт у машинозчитуваному вигляді:
```bash
digna project import-ds ProjectB my_export.json --output-format json --output-file import_report.json
```

Звіт охоплює чотири рівні об'єктів — джерело даних, визначення набору даних, атрибут і правило перевірки — і для кожного містить дію імпорту, результат, ідентифікатор отриманого об'єкта та будь-які додаткові відомості.

### project plan-import-ds

Команда `project plan-import-ds` показує попередній перегляд імпорту джерел даних до цільового проєкту: які об'єкти було б створено, оновлено чи пропущено, — не змінюючи при цьому нічого. Вона приймає той самий файл експорту й ті самі параметри звітування, що й [`project import-ds`](#project-import-ds), і додатково подає номер кроку для кожного запланованого об'єкта.

#### Використання команди
```bash
digna project plan-import-ds <PROJECT_NAME> <EXPORT_FILE> [OPTIONS]
```

#### Аргументи
- **PROJECT_NAME**: Назва цільового проєкту (обов'язковий).
- **EXPORT_FILE**: Шлях до файлу експорту (обов'язковий).

#### Параметри
- `--output-file`, `-o`: Файл, до якого записується план імпорту. Без нього план виводиться до stdout.
- `--output-format`, `-f`: Формат плану імпорту — `table`, `json` або `csv` (типово: `table`).

#### Приклад
```bash
digna project plan-import-ds ProjectB my_export.json
```

## Керування інспекціями

---

### inspection run

Команда `inspection run` створює запит на інспекцію для проєкту та діапазону дат, а потім — залежно від указаних параметрів — або очікує на нього, або одразу завершується, або виконує інспекцію у власному процесі.

Є три режими виконання:

- **Типовий (без прапорця)**: запит ставиться в чергу для серверної частини, а CLI опитує його кожні дві секунди, виводячи перебіг завдань, доки інспекція не досягне кінцевого стану. Потрібен запущений `digna serve`, інакше запит ніхто не підхопить.
- **`--async-mode`**: запит ставиться в чергу, а його ідентифікатор виводиться негайно. Для стеження скористайтеся [`inspection status`](#inspection-status).
- **`--bypass-backend`**: інспекцію виконує сам процес CLI, і вона не ставиться в чергу, тож запущений сервер не потрібен.

`--async-mode` і `--bypass-backend` є взаємовиключними.

У будь-якому режимі команда завершується ненульовим кодом завершення, якщо інспекція не була успішно завершена.

#### Використання команди
```bash
digna inspection run <PROJECT_NAME> <START_DATE> <END_DATE> [OPTIONS]
```

#### Аргументи
- **PROJECT_NAME**: Назва цільового проєкту (обов'язковий). Назва має збігатися точно.
- **START_DATE**: Початкова дата діапазону у форматі `YYYY-MM-DD` (обов'язковий).
- **END_DATE**: Кінцева дата діапазону у форматі `YYYY-MM-DD` (обов'язковий).

#### Параметри
- `--table-name`: Обмежує інспекцію одним джерелом даних проєкту, вказаним за назвою цього джерела. Без нього інспектуються всі джерела даних проєкту.
- `--async-mode`: Ставить інспекцію в чергу й виводить ідентифікатор запиту замість того, щоб очікувати на нього. Не можна поєднувати з `--bypass-backend`.
- `--bypass-backend`: Виконує інспекцію безпосередньо в процесі CLI замість того, щоб ставити її в чергу для серверної частини. Не можна поєднувати з `--async-mode`.

#### Приклад
```bash
digna inspection run ProjectA 2024-01-01 2024-01-31
```

Щоб надіслати асинхронну інспекцію:
```bash
digna inspection run ProjectA 2024-01-01 2024-01-31 --async-mode
```

Щоб проінспектувати одне джерело даних:
```bash
digna inspection run ProjectA 2024-01-01 2024-01-31 --table-name orders
```

#### Приклад виводу
Типовий режим:
```text
Inspection request submitted. Waiting for completion (Request ID: 1024)...
Progress: 3/10 tasks completed (0 failed)
Progress: 10/10 tasks completed (0 failed)
Inspection completed successfully.
Inspection successful for project: ProjectA
```

Асинхронний режим:
```text
Inspection request submitted successfully. Request ID: 1024
```

### inspection status

Команда `inspection status` запитує стан і перебіг завдань запиту на інспекцію за його ідентифікатором.

#### Використання команди
```bash
digna inspection status <INSPECTION_REQUEST_ID>
```

#### Аргументи
- **INSPECTION_REQUEST_ID**: Числовий ідентифікатор запиту на інспекцію (обов'язковий).

#### Приклад
```bash
digna inspection status 1024
```

#### Приклад виводу
```text
Inspection Request ID: 1024
Status: Running
Project ID: 7
Date Range: 2024-01-01 to 2024-01-31
Progress: 3/10 tasks completed (0 failed)
```

### inspection abort

Команда `inspection abort` запитує скасування запитів на інспекцію, які виконуються або очікують. Вона записує подію зупинення для кожного відповідного запиту; діє за нею серверна частина, тож переривання є проханням зупинитися, а не негайним припиненням.

#### Використання команди
```bash
digna inspection abort [INSPECTION_REQUEST_ID] [OPTIONS]
```

#### Аргументи
- **INSPECTION_REQUEST_ID**: Ідентифікатор запиту на інспекцію, який потрібно перервати. Обов'язковий, якщо не вказано `--killall`.

#### Параметри
- `--killall`: Перериває всі запити на інспекцію, які виконуються та очікують. Має пріоритет над ідентифікатором запиту, вказаним разом із ним.

#### Приклад
Щоб перервати конкретний запит:
```bash
digna inspection abort 1024
```

Щоб перервати всі активні інспекції та ті, що стоять у черзі:
```bash
digna inspection abort --killall
```

#### Приклад виводу
`--killall` повідомляє про виконане; переривання одного запиту нічого не виводить і сигналізує про успіх своїм кодом завершення.
```text
All running and pending inspections have been aborted.
```

### license check

Команда `license check` перевіряє файл `license.toml`, звіряючи його підпис із відкритим ключем, який постачається разом зі встановленням, і переконуючись, що термін його дії не минув. Вона не читає конфігурації застосунку, тож працює й до того, як налаштовано `config.toml`.

#### Використання команди
```bash
digna license check
```

#### Приклад виводу
```text
License is valid
```

Недійсний підпис і ліцензія з вичерпаним терміном дії повідомляються як окремі помилки, обидві з кодом завершення 1.

### serve

Команда `serve` запускає сервер REST API ***digna*** разом із фоновим планувальником інспекцій і менеджером інспекцій. Під час запуску вона також позначає як невдалі всі інспекції, які репозиторій досі вважає такими, що виконуються, оскільки від попереднього процесу ніщо не могло вціліти.

Команда працює на передньому плані, доки її не зупинять.

#### Використання команди
```bash
digna serve [OPTIONS]
```

#### Параметри
- `--address`: Мережева адреса, до якої прив'язується сервер API (типово: `127.0.0.1`).
- `--port`: Номер порту для прослуховування (типово: `8000`).

#### Приклад
```bash
digna serve --address 0.0.0.0 --port 8000
```

#### Приклад виводу
```text
Server running on http://0.0.0.0:8000
```
